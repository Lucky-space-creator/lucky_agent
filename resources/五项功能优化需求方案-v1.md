## 一、回复消息格式重构（思考折叠 / 执行面板只留步骤列表 / 正文只留总结）

### 1.1 现状与问题

| 位置                            | 现状                                                                           | 问题                                         |
| ----------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------ |
| 执行面板 `ChatView.vue` run-panel | 展示 phase、思考（thoughts）、进度日志（logs）、工具调用计数、任务列表（plan）                           | 内容过多；用户要求**只展示分步步骤列表，详细的内容可以放进折叠中**        |
| 回复消息 `MessageItem.vue`        | 正文（content_delta 流式）+ 查看文件 + 工具调用 + PlanCard + AskCard；思考过程**不在消息内**（只在执行面板） | 思考应**默认折叠放进回复模块**；正文前后的 plan/分析类内容不应出现在回复区 |
| 最终回复正文                        | `content_delta` 逐字追加 + `stop` 时 `p.summary` 覆盖                               | 用户要求只看到**总结回复**；分析/规划等过程文本归入思考内容           |

### 1.2 实现方案

**（1）执行面板瘦身 —— 只留任务列表**

- `ChatView.vue`：删除 run-panel body 中的「思考」「进度」两个 section 与思考/工具计数；面板仅渲染 `runPanel.plan`（步骤列表，状态点 + 中文标签）。
- 面板头部简化：只显示「任务进度」+ `done/total` 计数；无 plan 时整块不渲染（沿用现有 `v-if="chat.running || plan.length>0"`）。
- `runPanel.thoughts` / `logs` **不删除数据结构**（后端事件照收），仅转移展示位置：thoughts 落到消息折叠区（见下），logs 移入透明监控面板（右侧「监控指标」）或直接丢弃展示（待确认，见 §7-1）。

**（2）回复模块内新增「思考过程」折叠区**

- `MessageItem.vue`：在正文**下方**（或上方，待确认 §7-1）新增折叠组件，默认收起：
  - 头部：`已深度思考（N 次）` + chevron；
  - 展开后渲染本轮 thoughts 列表（数据源从 `runPanel.thoughts` 在 `stop` 时快照到 `item.thoughts`，历史会话加载时该区为空——历史思考是否持久化见 §7-2）。
- 样式复用现有 `.msg__thoughts` 残留 CSS（左竖线缩进、细字），改为 `details/summary` 或受控 ref 折叠。

**（3）正文只留总结**

- 后端：确认最终回复只经 `content_delta`/`stop.summary` 输出总结正文（thin 模式的「答案文本卡死守卫」已保证；reactor 主环需复核一次，见 §7-3）。
- 前端：`PlanCard` 从回复正文区移除，plan 只在执行面板展示；AskCard、文件总览保留（属结果性信息，是否保留见 §7-1）。

### 1.3 改动清单

- `web/fronted/src/views/ChatView.vue`：run-panel 模板瘦身。
- `web/fronted/src/stores/chat.ts`：`stop` 事件时把 `runPanel.thoughts` 快照进 `item.thoughts`。
- `web/fronted/src/components/chat/MessageItem.vue`：新增思考折叠区；移除 PlanCard。

## 二、会话命名：首条消息精简（可 LLM）

### 2.1 现状

- 前端 `chat.ts submit()`：`session.title = content.slice(0, 24)`，纯截断、含换行/代码块时观感差。

### 2.2 实现方案（两层：前端兜底 + 后端 LLM 精简）

1. **前端兜底（立即可见）**：首条消息命名时取首行、去 markdown 符号、压缩空白后 `slice(0, 24)`。
2. **后端 LLM 精简（最终命名）**：
   - `ConversationManager` / orchestrator 收尾时（沿用记忆总结的 `finally` 异步 `boundedElastic` 模式），若该会话标题仍是「新会话」或前端截断标题，则用**记忆管理 Agent 端点**（无则回退主模型）做一次极短调用：输入首条用户消息，输出 ≤16 字标题。
   - 写回 `SessionRepository` 的会话元数据（`updateSession` 已有 title 字段，链路现成）。
   - SSE `stop` 事件 payload 增加 `sessionTitle`（可选字段），前端收到后同步本地 `sessions` 列表；不做则下次加载会话列表自然刷新。

- 复用口径：与记忆总结同频（每轮一次但**只在首轮**触发）、走 memory 角色 LLM、失败静默保留截断标题。

### 2.3 改动清单

- 后端 `agent-core/.../service/ConversationManager.java`（或 thin 主循环收尾处）：首轮后异步生成标题 + 回写。
- 后端 `agent-web/.../ChatController` / SSE stop 事件：可选携带 `sessionTitle`。
- 前端 `chat.ts`：stop 事件同步标题；`submit` 兜底命名改为「首行清洗 + 截断」。

## 三、LLM 条件选择（1.2.3 选项 + 其他补充，用户选择后继续）

### 3.1 现状

- 只有危险操作确认 `AskCard`（允许/拒绝二选一），无通用「多选项 + 自定义补充」交互。

### 3.2 实现方案

**事件契约（新增 `options` 事件）**

```json
{
  "type": "options",
  "payload": {
    "question": "选择实现方案",
    "options": [
      { "id": "1", "label": "方案A：…", "detail": "…" },
      { "id": "2", "label": "方案B：…", "detail": "…" }
    ],
    "allowCustom": true,
    "customHint": "其他补充"
  }
}
```

**后端**

- LLM 输出约定：在系统提示词中约定「需要用户决策时输出 JSON 块 `options …`」，orchestrator 检测到该块 → 解析、从正文剥离、发 `options` 事件并挂起（复用 ASK 挂起/断线恢复机制 D7：`.tmp/pending-ask.jsonl` 同款，或复用现有 `pendingConfirmGoal` 思路）。
- 用户选择回传：前端把选择作为一条普通用户消息提交（`extra.optionPick = true`），后端将其注入上下文继续对话 —— **不做新的确认状态机**，保持「薄主循环」原则。
- 提示词内同时要求提供「其他/补充」入口（`allowCustom`）。
- **超时兜底（决策 ⑥）**：挂起超时（`core.options-timeout-sec`，默认 300s）后用户仍未选择，由 `ConversationManager` 的定时任务取出**推荐项**（无 `recommended` 则首项）作为用户输入自动续跑；用户在超时前作出任何应答（点选/自定义/直接发消息）即消费挂起态，超时任务静默失效（`ConcurrentMap.remove(k,v)` 保证与用户输入互斥，不重复续跑）。

**前端**

- 新组件 `OptionCard.vue`（结构类似 AskCard）：渲染问题 + 编号选项按钮 + 「其他」输入框（`allowCustom` 时显示）。
- `chat.ts`：`applyEvent` 新增 `case 'options'` → 写入 `item.options`（新 `ChatItem` 字段）；`pickOption(item, opt)` → `submit(所选文本)`，卡片转为已选态（`pickedId` 锁定，不可重复选）。
- 运行中防重：`chat.running` 时选项禁用。

### 3.3 改动清单

- 后端：提示词（`ReactEngine.phaseInstruction`）+ `OptionsBlockParser`（新）+ `AgentEventType.OPTIONS` / `AgentEvent.options(...)` / `OptionItem` + `Orchestrator` 的 options 状态透传（直连/步骤两路）+ `ConversationManager` 的挂起登记与超时自动选优 + `PresetResolver.optionsTimeoutSec()` + `application.yml` 的 `core.options-timeout-sec`。
- 前端：`OptionsCard.vue`（新）、`chat.ts`（`OptionsView`/`OptionItemView`、`case 'options'`、`pickOption`）、`MessageItem.vue`、`api/types.ts` 与 `api/sse.ts`（`AgentEventType` 增 `'options'`）。
- 测试：`OptionsBlockParserTest`（8 例，全绿）。

**本项状态：已完成（§三）** —— 后端 `clean test` 全绿（213 用例 / 0 失败），前端 `vue-tsc --noEmit` 通过。

## 四、工作流 MVP：重构到 LangGraph4j

### 4.1 现状与问题

- `agent-workflow` v1 为**自研引擎**（`DagCompiler` Kahn 拓扑 + `WorkflowEngine` 手写调度），**未使用 LangGraph4j**；7 类节点执行器、条件求值器、触发器齐但引擎层重复造轮子。
- **未接入宿主**：`agent-web` 未依赖该模块，`/api/workflows` 未上线；前端 `WorkflowView.vue` 已有界面但无真实后端。
- `agent-core` 已有 LangGraph4j 集成经验（`LangGraphOrchestrator` 用 `org.bsc.langgraph4j.StateGraph`，D33 收敛后与 thin 共享运行时）。

### 4.2 实现方案（MVP：基础组件 + LangGraph4j 引擎）

**原则**：引擎层换成 LangGraph4j `StateGraph`，删掉自研拓扑/调度；保留领域模型与 REST/SSE 契约；通过既有集成缝隙（`LlmAdapter`/`ToolAdapter`）接入宿主真实能力。

**基础组件（节点执行器，MVP 先做 5 类）**

| 组件          | 类型        | 说明                                                               |
| ----------- | --------- | ---------------------------------------------------------------- |
| START / END | start/end | 图起止                                                              |
| LLM 节点      | llm       | 单步模型调用（走 `ModelGateway`，含重试/熔断），输出写 state                        |
| 工具节点        | tool      | 调用既有 `ToolRegistry`/执行臂（受权限硬边界约束）                                |
| 条件路由        | condition | LangGraph4j 条件边（复用现有 `ConditionEvaluator` 安全子集做表达式求值）            |
| 模板变量        | —（内建）     | `${nodeId.field}` 点路径映射，复用 `MappingEvaluator`/`TemplateRenderer` |

> 人工确认节点（interrupt）与子流程（subflow）列为 MVP 后迭代；LangGraph4j 本身支持 interrupt 机制，属框架红利。

**改造步骤**

1. `agent-workflow` 增加 `org.bsc.langgraph4j:langgraph4j-core` 依赖（版本对齐 agent-core 现用版本）。
2. 新增 `LangGraphWorkflowEngine`：`WorkflowDef → StateGraph` 编译器（节点注册为 `AsyncNodeAction`，条件边用 `edge()` 映射），替换 `WorkflowEngine`+`DagCompiler` 的调度职责（`DagCompiler` 保留做**执行前静态校验**：结构/环/孤立节点）。
3. 状态对象 `WorkflowState extends AgentState`：承载 `variables`（全局作用域）、`nodeResults`、`status`。
4. 执行事件桥接：节点进入/退出/失败 → 现有 `WorkflowEventBus`（SSE 契约不变，前端零改动）。
5. 接入宿主：`agent-web/pom.xml` 加 `agent-workflow` 依赖；`LlmAdapter`/`ToolAdapter` 的宿主实现放 `agent-web`（或 agent-core 暴露 Bean），编译期 `@AutoConfiguration` 自动装配。
6. 前端 `WorkflowView.vue` 对接真实 `/api/workflows`（列表/新建（JSON 定义）/运行/实例详情+SSE 进度）。

**边界（MVP 不做）**：可视化拖拽画布、版本管理、并行分支汇聚语义增强、分布式触发器。定时触发沿用现有 `IntervalTrigger`。

### 4.4 实施进度（已落地）

**步骤 1–2（引擎重构）已完成**：

- 抽出公共骨架 `AbstractWorkflowEngine`（装配、实例生命周期、`runNode`/`skipNode`/`applyOutputs`/`triggered`、事件发布），**双引擎并存**：`WorkflowEngine`（legacy Kahn 调度，默认）+ `LangGraphWorkflowEngine`（`StateGraph` 调度）。配置项 `lucky.workflow.execution.engine=legacy|langgraph`，两者共用同一套执行器/适配器/事件契约/状态机，切换对 REST/SSE/前端透明。
- `DagCompiler` 保留为**执行前静态校验**（结构/环/端点），环检测异常原样抛出（`WorkflowException`），不再被 `safeExecute` 吞掉。
- **三条 LangGraph4j 硬约束（已踩实并写入项目记忆）**：① 节点 id 不得以 `__` 开头（`GraphStateException`），内部 START/END 图 id 用 `entry-`/`exit-` 前缀；② 节点返回值必须是**新构造的可变 Map**，返回 `Map.of()`/state 内部 map 会抛 `UnsupportedOperationException`；③ **fail-fast 必须落在所有出边**——无条件边直连会绕过失败判定，故全部出边统一走 `addConditionalEdges`，路由函数先判 `state.failed()` → 回 `end-fallback` → 框架 END。
- 语义差异（图原生）：条件未命中的分支**不被访问**（`nodeOf(...)` 为 null），而非 legacy 的「级联 SKIPPED」。

**步骤 5（宿主接入）已完成**：`agent-web/pom.xml` 加 `agent-workflow` 依赖，并在聚合 POM `web/app/pom.xml` 的 `dependencyManagement` 补 `${project.version}` 条目（缺失会直接报 `dependencies.dependency.version is missing`）。适配器缝隙已有 Noop 兜底（`@ConditionalOnMissingBean(LlmAdapter/ToolAdapter)`），故接入后 `agent-web` 编译与上下文装配通过。
`WorkflowProperties.Execution.engine` 默认 `legacy`，待灰度验证后再切默认值。

**测试**：`LangGraphWorkflowEngineTest` 5/5 绿（高分分支/低分分支/失败即终止/线性链/环检测）；agent-workflow 模块 **19/19 绿**；全仓 `mvn clean test` **219 用例 0 失败 BUILD SUCCESS**（15 模块）；`-pl agent-web -am test` EXIT=0。

**待办**：① 宿主侧真实 `LlmAdapter`（桥接 `ModelGateway`/`ConversationCtx`）与 `ToolAdapter`（桥接 `ToolGateway`）；② 步骤 6：前端 `WorkflowView.vue` 对接真实 `/api/workflows`。

### 4.3 改动清单

- `web/app/agent-workflow`：引擎重构 + 依赖 + 校验器保留。
- `web/app/agent-web`：依赖接入 + Adapter 宿主实现。
- `web/fronted`：`WorkflowView.vue` 对接（已有页面基础）。

## 七、待确认不足点（请用户补充）

1. **思考区位置**：「思考过程」折叠区放回复**上方**还是下方？执行面板去掉思考/进度后，进度日志是移到右侧「监控指标」面板，还是完全不展示？

3. **正文纯净度**：回复正文区目前还保留「查看的文件 / 变动的文件 / 工具调用」总览，是否也收进折叠区，正文只留纯文本总结？

6. **选项继续的语义**：用户选完 1/2/3 后，是作为普通用户消息继续（推荐，实现简单），还是需要严格挂起-恢复（同一轮不结束）？
7. **工作流节点范围**：MVP 的 5 类基础组件是否够？是否必须包含「人工确认 interrupt 节点」？
8. **设置页范围**：参照截图中的「个人主页/套餐与积分/快捷键/安全中心」等项是否需要占位展示（隐藏未实现项 vs 全部放出来）？

## 八、推荐方案（供拍板）

> 每条标注【推荐】默认选项；其余为备选。理由紧扣项目既有约定（薄主循环、本地优先、Web/CLI 共用内核、断线恢复 D7）。
> **决策确认（2026-09-21）**：① 思考区置正文下方+进度日志进监控面板（分阶段/子代理展示见 §九）；② 思考落盘只留分析/规划段；③ 文件工具总览收进折叠；④ 规则单文件分节+多文件高级；⑤ 预设按工作空间生效+全局默认；⑥ **选项=挂起+超时 LLM 自动选最优**；⑦ 工作流必含 interrupt 节点；⑧ 设置页**移除**套餐与积分/安全中心/快捷键，其余保留。

**1. 思考区位置与进度日志去向**
- 【已确认】思考折叠区放**回复正文下方**（正文 → 思考折叠 → 文件/工具总览 → meta）；执行面板去掉思考/进度后，进度日志**迁入右侧「监控指标」面板**（`TransparencyPanel` 已有 metrics 通道，加一个「运行日志」tab 即可），回复区与执行面板均不再展示。**分阶段/子代理模式的层级展示区设计见 §九**。
- 备选：思考区放正文上方（更接近"先思考后回答"叙事，但会让用户先看到折叠再看到答案，浏览效率低）。
- ⚠️ **可行性修正（2026-09-21 核验）**：`TransparencyPanel.vue` 是**纯指标组件**，仅渲染 `SessionMetrics`（token/轮次/工具/子代理计数），**无 free-text 日志通道**，也无 store 字段承载 `runPanel.logs`。因此"加个运行日志 tab"需新建日志数据流（store 增 `runLogs` + 组件加日志区），并非一行改动。**P1 建议**：进度日志**在 P1 直接不再展示**（指标面板已覆盖工具/轮次/子代理计数，free-text 日志属调试级信息），把"在监控面板加运行日志 tab"列为 **P1 之后按需补充**，避免 P1 范围膨胀。

**2. 历史思考持久化**
- 【推荐】**落盘**，但只持久化「分析/规划阶段」的关键思考（`task_plan` 之前的那批 thoughts），不落每轮增量噪声；随会话 JSONL 存进 `ChatItem.thoughts` 字段（`SessionRepository` 落盘时带上该数组，现有快照结构已支持）。刷新后可展开查看，成本可控（思考文本量远小于正文）。
- 备选：不落盘（仅当轮展示），实现最简单但刷新即失。

**3. 正文纯净度**
- 【推荐】文件查看/变动总览、工具调用也**收进折叠区**（合并为一个「执行详情」折叠块）；正文只留纯文本总结。`AskCard`（危险操作确认）**保留在正文区**（它是交互不是噪声）。
- 备选：仅收起思考、其余保留 —— 不够"只留总结"。

**4. 规则存储形态**
- 【推荐】默认「**单文件内 `## 规则名` 分节**」（`LUCKY.md` 扩为多节，Web textarea 直接编辑、diff 友好、与现机制兼容）；设置内提供「高级：使用规则目录（多文件）」开关，开启后改用 `~/.lucky_agent/rules/global/*.md` 与 `<workspace>/rules/*.md`。两类均支持项目规则多条。
- 备选：一律多文件 —— 对少量规则编辑体验差、Web 列表要维护多文件 CRUD。

**5. 预设生效范围**
- 【推荐】**按工作空间生效 + 一个全局默认预设**。默认读全局预设，各工作空间可覆盖（对齐现"工作空间绑定模型"的做法）；落 `settings.json` 持久化。
- 备选：仅全局 —— 多项目技术栈差异下不灵活。

**6. 选项继续语义**
- 【已确认·调整】选项采用**挂起（suspend）**而非普通消息：复用 D7 `pending-ask` 挂起/恢复机制；服务端设**超时**（如 5 分钟），超时未选则 **LLM 自动从选项中挑选最优项**（标注 `recommended` 或置信度最高的一项）注入上下文继续，绝不无限等待。需新增 options 事件的挂起 + 超时自动选优恢复链路（比 P3 原计划的"普通消息继续"略重，但满足"挂起"诉求）。
- 备选：纯普通消息继续（无超时自动选）—— 用户未选则对话卡死，已否决。

**7. 工作流节点范围**
- 【推荐】MVP **必含人工确认 interrupt 节点**（LangGraph4j `interrupt` 是框架红利，成本低且用户工作流普遍需审核）；子流程 subflow 放到 MVP 之后。
- 备选：MVP 不含 interrupt —— 会逼用户用危险操作绕路，体验差。

**8. 设置页范围**
- 【已确认·调整】参照截图导航中，**移除**「套餐与积分」「安全中心」「快捷键」三项；其余分组（通用 / 个人主页 / 外观 / 个性化 / 记忆与进化 / 智能体 / 模型 / 助理设置 / 数据管理 / 应用管理 / 关于）保留。未实现项仍显式「敬请期待/置灰」，不隐藏。
- 备选：隐藏未实现项 —— 用户以为功能缺失，排查成本高。

## 九、分阶段 / 子代理模式的展示区设计（§八.1 补充）

**问题**：当任务被 orchestrator 拆成多阶段（PLAN→ACT→验证）或派发子代理（SubAgentSpec）时，"执行面板只留步骤列表 + 正文只留总结"前提下，这些层级/子代理结果该展示在哪？

**原则**：沿用"消息只留总结、执行面板只留步骤列表"，把层级关系**收敛进执行面板**，不污染正文。

**1. 数据模型扩展**
- `TaskPlanView` 增加可选 `children?: TaskPlanView[]`（子步骤/子代理任务）与 `phase?` / `owner?` 字段（`owner`=主代理/子代理名）。推荐**嵌套 children**，前端渲染最简单。
- 事件：`task_plan` / `task_progress` 扩展 payload 支持 `parentId` / `phase` / `owner`；子代理结论（`summaryOnly`）作为父任务子节点，其内部工具调用/思考归入该子节点折叠。
- 子代理硬约束（thin 模式已有：并发 ≤4、深度 ≤2）即面板渲染上限，不会爆炸。

**2. 执行面板（唯一展示层级处）**
- 一级分组标题 = 阶段（分析/规划/执行/验证）或子代理名（如「子代理·检索」），下挂该组任务列表。
- 任务项可展开（chevron）：展开后显示该任务/子代理的内部步骤（工具调用、子结果摘要）。
- 面板顶部仍只显示 `done/total` 计数，保持"任务列表"定位。

**3. 消息区**
- 正文只留最终总结。
- 新增一个**默认折叠**的「分阶段 / 子代理执行详情」块（与思考折叠并列、置于其下方）：展开后按阶段/子代理分组展示子结果摘要（非完整思考），保证正文纯净且细节可追溯。

**4. 持久化**
- 任务层级随会话 JSONL 落盘（扩展 `ChatItem.plan` 为嵌套结构），刷新后可展开查看。
