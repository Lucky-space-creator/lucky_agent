# agent-memory 模块实现文档

> 对应需求文档：§3.0 目录规范、§3.2 用户层面记忆、§3.3 平台层面记忆、§3.4 双轨协同、§3.5 与 LangChain4j/LangGraph4j 结合

## 一、模块定位

`agent-memory` 负责**双轨记忆**（用户层面 + 平台层面）的存储、检索、萃取与持久化。所有数据只在本机内存 + 本机文件，无任何上行通道（隐私红线 R4）。

**责任边界**：
- 记忆的写入/检索/压缩/持久化。
- 平台记忆只读加载（随发行包）。
- 不负责权限裁决、不负责工具执行。

## 二、实现框架（分层）

```
agent-memory
├── api/
│   ├── MemoryStore.java      # 记忆读写契约
│   ├── MemoryRetriever.java  # 检索召回契约
│   └── dto/ MemoryEntry, RecallResult
├── pipeline/
│   ├── NoiseFilter.java      # 噪声过滤层
│   ├── Cleaner.java          # 数据清洗/结构化抽取/脱敏
│   ├── FactExtractor.java     # 事实萃取（置信度/冲突检测/去重）
│   └── DecayManager.java     # 遗忘/衰减机制
├── store/
│   ├── UserMemoryStore.java       # 用户层面（<frameworkRoot>/.memory/）
│   ├── PlatformMemoryStore.java   # 平台层面（<frameworkRoot>/.platform/ 只读）
│   └── LocalFileBackend.java      # JSONL + 本地向量索引
├── retract/  (可选)
│   └── Compressor.java       # 长记忆下沉（配合 4.13）
└── config/  MemoryConfig.java
```

**目录落盘（§3.0）**：
- 用户记忆：`<frameworkRoot>/.memory/`（JSONL + 本地向量索引）。
- 平台记忆：`<frameworkRoot>/.platform/`（随包内置，只读）。

## 三、实现思路（核心设计）

### 3.1 总体分层管线（§3.1）

```
原始输入/产出（内存）
  → 噪声过滤（规则+轻量判别）
  → 数据清洗（结构化抽取/脱敏）
  → 分层记忆（按归属拆用户/平台）
  → 事实萃取（置信度+冲突+去重聚合）
  → 沉淀事实（高置信进本地知识库）
横切：检索层 + 遗忘/衰减，作用于两轨
```

### 3.2 双轨隔离（§3.4）

| 维度 | 用户层面 | 平台层面 |
|---|---|---|
| 归属 | 本机用户 | 框架预置→本机加载 |
| 优先级 | 个性化覆盖 | 规范性兜底 |
| 冲突 | 用户优先（除非 FORCE） | FORCE 安全/合规不可覆盖 |
| 写入 | 用户交互累积（仅本机文件） | 框架发行包 |

**隐私防火墙（机制）**：用户层面记忆**只写本机文件，无上行通道**；平台记忆更新走"框架升级包"而非"用户数据回传"。从架构上物理隔断用户记忆上漂（R4）。

### 3.3 持久化（必选，§3.0/§3.2）

- 运行态驻留本机内存（低延迟）。
- 跨会话必选落盘 `<frameworkRoot>/.memory/`（JSONL + 本地向量索引），进程退出/重启加载恢复。
- 不落云端。

### 3.4 检索与注入（§3.5）

- 记忆作为 Memory Module/Tool，经 `agent-core` 的 `ToolGateway` 注入。
- 短期记忆绑 Conversation/session；长期与沉淀事实作外部 Provider（后端=本机文件索引）。
- 注入时按用户+平台两层面分别召回并打标；启动时从 `<frameworkRoot>/.memory/` 与 `<frameworkRoot>/.platform/` 加载。

### 3.5 本地向量索引

- 不引入云端向量库；用本机轻量向量（如本地 HNSW / 简单余弦索引）存 `<frameworkRoot>/.memory/`。
- 文件格式：`<userId>/mem.jsonl`（追加写）+ `<userId>/index.bin`（向量索引，可重建）。

## 六、具体设计

> 核心思路：把记忆实现为 LangChain4j 的 Memory Module/Provider，双轨只是两个 Provider；存储用 JSONL + 本地轻量向量，不引云端。本模块只做职责、流程与边界层面的设计，不涉及具体代码实现。

### 6.1 复用 LangChain4j 的方式
- 记忆对外表现为 LangChain4j 的 Memory 接口实现，由 core 注入会话；召回结果作为上下文参与推理。
- 长期/沉淀事实作为外部 Memory Provider，后端即本机文件索引。

### 6.2 双轨存储职责
- **用户轨存储**（`<frameworkRoot>/.memory/`，可读写）：负责写入用户交互累积记忆，追加写 JSONL 并同步更新本地向量索引。
- **平台轨存储**（`<frameworkRoot>/.platform/`，只读）：仅从框架发行包加载，写入即拒绝（ReadOnly）；保证平台规范性建议不被用户数据污染。
- **本机文件后端**：统一承担 JSONL 追加与本地向量检索（HNSW/余弦）的 IO，与上层存储逻辑解耦，便于替换索引实现。
- **处理管线**：噪声过滤（筛掉低质输入）→ 事实抽取（置信度/冲突/去重）→ 衰减遗忘（低置信周期遗忘），仅用户轨走写、平台轨只加载。

### 6.3 落盘格式
- `<userId>/mem.jsonl`：追加写，每行 `{ts, track:USER|PLATFORM, content, confidence}`。
- `<userId>/index.bin`：本地向量索引（HNSW/余弦），可重建，不强制持久正确性。

### 6.4 设计模式应用
- **策略模式**：用户轨与平台轨实现同一存储契约，召回时两策略分别执行。
- **桥接模式**：文件后端与"向量检索/JSONL 文本"解耦，便于换索引实现。
- **模板方法**：事实抽取固定"置信→冲突→去重"骨架。
- **仓储模式**：文件后端隔离文件 IO 细节。

### 6.5 验收点（具体）

- [ ] 向平台轨存储发起写入被拒绝，且用户交互日志中无 `<frameworkRoot>/.platform/` 写记录（只读红线）。
- [ ] 进程重启后召回结果非空（从 `<frameworkRoot>/.memory/` 加载成功），且向量索引可重建。
- [ ] 召回结果带 `track` 标记，用户偏好条目在平台建议冲突时优先（FORCE 项除外）。
- [ ] 并发写入由 common 的读写锁保护，无 JSONL 行交错。
- [ ] 单元测试模拟网络出站，断言无任何上行请求（隐私红线 R4）。
- [ ] 作为 LangChain4j/LangGraph4j Memory 注入后，会话上下文出现召回内容。

## 七、会话消息 → 记忆系统同步策略（问题 3：实时还是定时）

> 结论：**双机制——"按消息实时写入"打点 + "定时/周期落盘压缩"兜底**，二者职责不同，不互斥。

### 7.1 按消息实时同步（主路径）
- 每产生一条用户消息 / 一条 Observation（工具结果）/ 一个 ASK 节点，core 立即调用 memory 的 `append` 写入**内存缓冲 + JSONL**（`<frameworkRoot>/.memory/`）。这样断点、刷新、崩溃都不丢本轮上下文，且召回低延迟。
- 实时写入只做"追加"，**不做**重计算（噪声过滤/向量化可异步），保证主链路不被记忆处理拖慢。

### 7.2 定时落盘 / 周期压缩（副路径，兜底与优化）
- **定时刷盘**：内存缓冲按周期（如每 30s 或缓冲达阈值）批量 fsync 到 `mem.jsonl`，避免每条都落盘的性能开销（R7 持久化）。
- **周期向量化**：新写入的文本在后台定时做向量 upsert（检索需求不急时），检索时若索引未更新则回退文本匹配。
- **周期压缩**：**阈值触发为主、周期兜底为辅**——core 在每次模型调用后实时检查上下文占用率，**≥90%（`model.context.threshold`）即触发压缩**（保留"事实"丢弃"过程"，保全计划/安全约束/关键结果）；周期任务仅作兜底，处理会话空闲期未被触发但已逼近上限的旧记忆（如跨天长会话），避免长会话持续撑大占用率。

### 7.3 为什么不纯定时
纯定时（如每分钟）会导致崩溃丢一分钟、召回滞后；纯实时每条 fsync 又太慢。故采用"实时追加 + 定时刷盘/压缩"组合。

### 7.4 验收点
- [ ] 一条用户消息发出后，内存缓冲立刻可见，30s 内 `mem.jsonl` 出现该行（实时+定时双验证）。
- [ ] 进程崩溃重启后，崩溃前实时追加但未刷盘的消息可由缓冲恢复或至少不破坏已有 JSONL。
- [ ] 长会话触发周期压缩后，旧过程类记忆被摘要，召回内容仍含关键事实。
- [ ] 上下文占用率 ≥90%（`model.context.threshold`）时压缩被实时触发（无需等周期任务），压缩后占用率回落。

## 八、记忆框架分层操作步骤（问题 4：每一步思路）

> 双轨只是"两条存储"，真正的核心是**写入与召回各自经过的分层管线**。每一步都放在本模块，职责如下。

### 8.1 写入管线（用户轨）
1. **采集（Collect）**：core 推送本轮 Observation/消息，标记 `track=USER`。
2. **噪声过滤（NoiseFilter）**：丢弃低质（空/重复/纯报错栈）输入，减少污染。
3. **事实抽取（FactExtractor）**：从文本中抽取"事实"并赋置信度；冲突检测（与已有记忆矛盾时降级旧条）；去重（相似事实合并）。模板方法固定"置信→冲突→去重"。
4. **衰减（DecayManager）**：低置信事实周期性降权，长期不印证则遗忘。
5. **落盘（Backend）**：追加 `mem.jsonl` + 异步 upsert 向量索引。

### 8.2 召回管线（双轨合并）
1. **查询归一**：把当前意图向量化。
2. **双轨分别召回**：用户轨与平台轨各按相似度召回 Top-K。
3. **融合排序**：用户偏好优先于平台建议（除非平台项标 `FORCE`），输出带 `track` 标记的结果。
4. **注入**：作为 Memory Provider 注入 core 的 system prompt 召回上下文层。

### 8.3 平台轨的特殊处理
平台轨仅在发行包加载，跳过步骤 2-4 的写流程，只参与召回步骤 2-3，保证"平台规范不可被用户数据覆盖/污染"。

### 8.4 验收点
- [ ] 写入一条"高噪声"输入，噪声过滤后不进入 `mem.jsonl`。
- [ ] 写入与已有记忆冲突的新事实，旧条置信度下降（融合排序时排序靠后）。
- [ ] 召回结果中用户偏好项排在平台建议前（FORCE 项除外），且均带 `track` 标记。
