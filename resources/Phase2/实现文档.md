# Phase 2 实现文档：体验与安全 + 降本

> 关联需求：§4.6 缓存（仅3天/工具结果）、§4.7 执行回退、§4.13 上下文压缩、§5.2 隐私合规、§6 Token 治理、§4.14 模型 Key/URL 本机加密存储（PBKDF2/OS 密钥链）；八项差距 D14 权限增强、D16 多级压缩、D17 提示词缓存。
> 风险闭环：缓存陈旧（R5）、Key 泄露防护（本机加密存储）。

## 1. 阶段目标
在主链路（Phase1）之上补全安全与成本优化：权限增强（symlink 双路径、复合命令拆分、OS 沙箱、电路断路器）、提示词缓存（cache_control/inherit）、五级压缩流水线补齐、Token 计量与熔断、缓存、本机执行回退、隐私合规、模型 Key 管理增强（OS 密钥链/轮换/重填）。提升体验与安全性，压低模型成本。

### 1.1 本阶段新增能力

- 权限：执行臂/规则链补 symlink 双路径检查、复合命令拆分（Apache Commons Exec）、OS 级沙箱、bypass 模式电路断路器。
- 提示词缓存：按模型供应商能力接入 `cache_control` 断点，子代理 `model: inherit` 共享父会话缓存。
- 压缩：补齐 Microcompact、Snip、Reactive Compact，引入 `preservedSegment` 保留最近 N 轮；PreCompact/PostCompact 归档；压缩连续失败熔断（如 3 次）。
- Token 与熔断：jtokkit 计量 token，Resilience4j 或简单计数器做压缩/模型调用熔断。

## 3. 缓存模块（§4.6 / D5）
- **会话消息缓存**：仅保存用户**最近 3 天**对话消息与会话上下文，按 `userId + workspaceId` 隔离，存本机内存（Caffeine）。
- **3 天 TTL 清理**：`TtlSweeper` 定时任务（如每 6h）扫描，超 3 天消息/会话清除；落盘 `.cache/` 同样按 3 天过期。
- **工具结果缓存**：参数 + `文件 hash + 会话标识` 作指纹，同参数不重跑；陈旧（文件变更 hash 变）自动未命中。
- **降级**：缓存异常跳过直接调用，不抛阻断。

### 3.1 缓存数据结构（伪）
```
CacheKey { userId, workspaceId, sessionId, opFingerprint(文件hash+会话标识) }
CacheVal { result, expireAt( now+3d for msg ), version }
```

## 4. 执行回退模块（§4.7）
- **检查点**：关键操作（写/删/覆盖）前在 `.rollback/<workspaceId>/` 生成快照（文件版本/状态点）。
- **索引**：`rollback-index.jsonl` 记录 `{checkpointId, workspaceId, ts, affectedFiles[], parentId}`。
- **撤销**：用户"一键撤销"→ 选检查点 → 还原本机快照；粒度=检查点，可逐步回退。
- **无消息队列**：纯本机文件快照 + 索引，回退即还原。

## 5. 上下文压缩（§4.13）
- `TokenMeter` 监控本机内存 token；**上下文占用率（会话已用 token ÷ 模型上下文窗口）≥ 90% 阈值（`model.context.threshold`，默认 0.9）时自动触发**滑动窗口/摘要/下沉。
- 阈值触发由 core 每次模型调用后检查，不等定时任务；压缩后占用率回落继续。
- 保全：计划/安全约束/关键结果不下沉。
- 下沉接口交给 agent-memory（Phase1 双轨持久化）。
- 用户无感，结合缓存降本。

## 6. Token 治理（§6）
ToC 单模型前提：主手段 = 上下文压缩 + 语义/工具缓存 + Prompt 精简 + REACT 步数上限；分层模型仅多模型增强（Phase3）。
- 工具按需召回 Top-K（Phase3 Skill 落地后生效，本阶段预留钩子）。
- 前端展示 token/调用数（透明化基础版）。

## 7. 模型 Key 管理增强（基础加密已在 Phase 1）
- Phase 1 已完成 Key/URL 加密落盘（PBKDF2/OS 密钥链 + AES-GCM），明文不落盘。
- Phase 2 补充 OS 密钥链切换、Key 轮换、重填流程与无明文残留检查。
- 不随包硬编码；口令丢失走"重填 Key"应急（Web 配置页提供入口）。
- 只要本机落盘加密 + 内存不外泄，即满足"Key 不泄露"，无需平台侧 ID/token 机制（R10 已删除）。

### 7.1 加解密流程（伪）
```
保存: cipher = AES-GCM.encrypt(derivedKey, plaintext); 写 .config/model.enc
读取: plain = AES-GCM.decrypt(derivedKey, read(.config/model.enc)); 用完置 null
derivedKey = PBKDF2(userPass, salt, 60000)
```

## 9. 技术需求方案与思路架构分析

> 本章对 Phase 2 的降本 / 安全 / 体验类技术需求展开方案与架构权衡。

### 9.1 缓存（§4.6 / D5 / R5）
**需求**：会话消息仅留 3 天；工具结果避免陈旧命中；异常不阻断。
**方案与思路**：
- **会话缓存（3 天 TTL）**：按 `userId+workspaceId+sessionId` 隔离存本机内存（Caffeine）；`TtlSweeper` 定时（如 6h）清理超 3 天消息/会话；落盘 `.cache/` 同样按 3 天过期。设计动机：用户数据全在本机，无云端 Redis；3 天窗口既保冷启动体验又防无限堆积占内存/磁盘。
- **工具结果缓存（指纹）**：key = 参数 + `文件hash + 会话标识 + 记忆版本`，同参数不重跑；文件变更 hash 变即失效（闭环 R5 陈旧命中）。
- **降级**：缓存异常跳过直接调用，不抛阻断——单机场景缓存是加速而非必需，降级优于失败。
- **架构**：`CacheGuard`（Caffeine 封装）在 `agent-common`，按用户/工作区隔离；未来换 Redis 仅换 `agent-common` 实现（与 §11 演进一致）。

### 9.2 执行回退（§4.7）
**需求**：关键操作可一键撤销，不引入消息队列。
**方案与思路**：
- **检查点快照**：写/删/覆盖前在 `.rollback/<workspaceId>/` 生成快照（文件版本/状态点），与 Phase1 的 `workspaceId` 隔离一致，多工作区不串扰。
- **索引**：`rollback-index.jsonl` 记 `{checkpointId, workspaceId, ts, affectedFiles[], parentId}`，支持逐步回退到任意检查点。
- **撤销 = 还原本机快照**，纯本机文件操作；无 RocketMQ（单实例无分布式事件解耦需求，§2 已明确不引入）。

### 9.3 上下文压缩（§4.13）
**需求**：Token 控制，关键信息安全。
**方案与思路**：
- `TokenMeter` 监控本机内存 token，**上下文占用率 ≥ 90%（`model.context.threshold`）自动触发**滑动窗口 / 摘要 / 下沉；占用率 = 会话已用 token ÷ 模型上下文窗口，由 core 每次模型调用后检查。
- **保全**：计划 / 安全约束 / 关键结果不下沉（防压缩破坏核心契约）。
- 下沉接口交给 Phase1 的 `agent-memory` 双轨持久化，复用既有存储，不新建设施。
- 用户无感，与缓存共同降本。

### 9.4 Token 治理（§6）
**需求**：ToC 单模型下压低成本。
**方案与思路**：
- **关键修正**：多数 ToC 用户仅单 Key/单模型，无法路由轻量模型。故主手段 = 上下文压缩 + 语义/工具缓存 + Prompt 精简 + REACT 步数上限；**分层模型仅多模型增强项**（Phase3），不设为默认预期。
- 工具按需召回 Top-K 钩子本阶段预留（等 Phase3 Skill 落地）。
- 前端展示 token/调用数（透明化基础版）。

### 9.5 模型 Key 管理增强（基础加密已在 Phase 1）
**需求**：Key 不泄露，支持 OS 密钥链、轮换与重填，不引入平台 ID/token 机制。
**方案与思路**：
- `CryptoUtil`：Phase 1 已完成 PBKDF2/OS 密钥链派生密钥 + AES-GCM 加密存 `.config/model.enc`，明文不落盘；Phase 2 增强 OS 密钥链切换、Key 轮换与重填。
- **内存纪律**：解密后仅本次调用使用，用完置 `null` 清引用；不随包硬编码（否则加密形同虚设）。
- 口令丢失走"重填 Key"应急（Web 配置页入口）。
- 设计动机：只要本机落盘加密 + 内存不外泄即满足"Key 不泄露"，无需平台侧 ID/token（原 R10 已剔除）；框架自身不存储不回传用户 Key，第三方模型风险由用户 Key 责任方承担（明示）。

### 9.6 隐私合规（§5.2）
**需求**：数据最小化，清记忆无残留。
**方案与思路**：
- "清除我的记忆"：删本机 `.memory/` + 内存清空 + `.cache/` 会话清理，三处一致清除。
- 前端明示"平台不存储用户内容"、第三方模型风险由用户 Key 责任方承担——把责任边界落到用户认知。

### 10.3 与原始需求文档的偏差说明（实现即事实源）

1. **TokenMeter 不依赖 jtokkit**：LangChain4j 1.19.0 未提供 `Tokenizer` 类，改为自包含字符启发式估算（`textOf` 用 `instanceof` 提取各消息类型文本），provider 无关、可测。
2. **复合命令拆分自研**：未引入 Apache Commons Exec，由 `CommandSplitter` 按 `&&`/`;`/`|`/换行拆分，契合"不引入额外中间件"边界。
3. **缓存/密钥落点模块调整**：`CryptoUtil` 能力实际沉淀于 `agent-model` 的 `KeyCipher`/`KeyVault`（非 `agent-common`），与"执行臂为最终裁决者"架构一致；`CacheGuard` 由 `agent-cache` 直接承载。
4. **压缩/熔断阈值**：压缩连续失败熔断阈值沿用 `TokenCircuitBreaker`（默认 3 次）与权限 `PermissionCircuitBreaker`（阈值 5），均在 `agent-core`/`agent-permission` 内可配。
5. **修复的真实缺陷**：`ModelConfigStore.load()` 原先仅恢复 `endpointUrl`，遗漏 `apiKeyPlain` 解密恢复，导致重填流程 `apiKeyPlain` 为 null；Phase2 已修复。
6. **`ToolGatewayTest` 并行断言复验失败并修复（2026-08-24）**：首验文档声称已用 `CountDownLatch` 栅栏将总耗时收敛到 `< 3×200ms` 且全量绿，但本轮干净复验实测 641ms（峰值并发=3，并行确实生效，仅绝对耗时超阈值），属脆弱时间硬阈值。修复：单条 `Thread.sleep(200)` → `120ms`、断言 `cost < 600` → `cost < 300`（串行累加 360ms，仍远小于"无并行"且卡紧并行收益），复验全量 `mvn test` 通过。
7. **前端 token 展示已落地**：`TransparencyPanel.vue` 经复验确认已存在并接入 metrics 接口，`vue-tsc`/`vite build` 通过，原 #11 "延后"标记撤销，改为 ✅。
