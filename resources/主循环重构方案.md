# 主循环重构方案：「薄主循环 + 厚运行时」

> 版本：v1.0　适用范围：`agent-core` 外层编排主循环（`Orchestrator` / `LangGraphOrchestrator`）
> 目标：主循环只保留「调 LLM → 执行工具/子代理 → 回填观察」三步；拆解、调度、验证、记忆、安全阀全部下沉为可插拔运行时组件。

---

## 1. 现有代码评估

以 `agent-core/src/main/java/com/lucky/agent/core/service/Orchestrator.java`（613 行）为样本，`run()` 单方法约 240 行，问题可归为六类：

| # | 问题 | 具体证据（代码位置） | 后果 |
|---|------|----------------------|------|
| 1 | **主循环过重** | `run()` 内联：安全阀检查、ASK 挂起、子代理规格构建+串行调度+摘要回灌、步骤拆分+逐任务执行+重试+回滚、取消检查、验证、早停、记忆管理、goal 改写 | 单方法混合 10+ 职责，维护成本高、分支组合爆炸 |
| 2 | **职责耦合** | 验证（`verificationChain.verify`）、记忆（`loopMemoryManager.manage`）、进度（`taskProgressTracker`）、预算（`RunBudget`）直接内联 | 替换任一能力都需改主循环；无法按场景装配 |
| 3 | **状态爆炸** | `hasSteps` × `hasSubAgents` × `ask/cancelled/error/stuck/aborted/success` 组合；`goal = verdict.continueGoal()` 在循环内被改写 | 状态路径组合难以穷举测试；goal 漂移导致行为不可预测 |
| 4 | **策略硬编码** | 「是否拆分」由 `planGenerator.parse` + `planValidator` 决定；重试次数、退避、置信阈值（`EarlyStopPolicy`）均写死 | 无法按任务/租户/模型切换策略 |
| 5 | **启发式内联** | `isAskingReply()`（关键词表 + 正则）、`normalize()`、`stuckLoop()` 直接写在主循环 | 启发式与编排逻辑耦合，调参需改核心代码 |
| 6 | **验证不可靠** | 主循环既做客观验证又做「达成度判定」，无客观证据时置信固定 0.5 | 结论不可量化，LLM 自评易被采信 |
| 7 | **双主循环漂移** | `Orchestrator`（reactor）与 `LangGraphOrchestrator`（langgraph）语义等价但各自实现 | 同一套逻辑维护两份，行为易漂移 |

**根因**：主循环既是「控制流」又是「能力实现」。要同时承载编排与所有横切能力，必然膨胀。

## 2. 目标架构设计

### 2.1 分层与包结构（已落地于 `com.lucky.agent.core.runtime`）

```
com.lucky.agent.core.runtime
├── contract/        统一契约
│   ├── ExecutionResult      所有执行路径的统一返回（状态/输出/产物/错误/指标/trace/元数据）
│   ├── ExecutionStatus      SUCCESS | FAILED | ASK | CANCELLED | BUDGET_EXHAUSTED | TIMEOUT
│   ├── Artifact / ExecutionMetrics / TraceContext / ToolCall
│   └── RuntimeContext       贯穿一次编排的运行时上下文（含预算、trace、事件发布）
├── budget/          分层预算
│   ├── BudgetLevel          GLOBAL | TASK | STEP | SUBAGENT
│   ├── BudgetScope          token/时间/重试 三类限制 + 用量
│   └── BudgetManager        四级作用域管理 + 自底向上累计 + 熔断
├── tool/            工具化（LLM 可调用）
│   ├── RuntimeTool          工具契约（name/description/schema/invoke）
│   ├── ToolRegistry         注册/清单/分发（SPI 收集 List<RuntimeTool>）
│   └── VerifyTool / MemoryTool   示例实现
├── middleware/      中间件链
│   ├── Middleware           6 个钩子 + order()，可 block 短路
│   ├── MiddlewareContext    钩子间可变载体
│   ├── MiddlewareChain      按 order 排序执行，deny 优先
│   └── BudgetMiddleware / LoggingMiddleware
├── strategy/        策略插件
│   └── StrategyPlugin       shouldDecompose / shouldSpawnSubAgents / verifier()
├── verify/          客观验证
│   ├── Verifier             name/objective/verify
│   ├── VerificationRequest / VerificationOutcome（含 confidence/objective/evidence）
│   ├── ExternalCommandVerifier   测试/lint/退出码（客观）
│   └── CompositeVerifier         客观优先，首个表态者胜出
├── memory/          记忆端口
│   ├── MemoryPort           recall / recordLongTerm / compact（+ 结构化字段常量）
│   └── NoopMemoryPort
├── loop/            运行时 + 薄循环
│   ├── AgentRuntime         厚运行时门面（中间件/工具/策略/验证/记忆/子代理)
│   ├── SubAgentPool         虚拟线程子代理池（并发上限 + 深度限制）
│   └── ThinAgentLoop        薄主循环（实现 AgentOrchestrator，三步）
└── AgentRuntimeConfiguration  运行时装配（@ConditionalOnMissingBean）
```

### 2.2 核心接口定义

**统一结果契约**（`ExecutionResult`，节选）：

```java
public record ExecutionResult(
        ExecutionStatus status, String output, List<Artifact> artifacts,
        String error, ExecutionMetrics metrics, TraceContext trace,
        Map<String, Object> metadata) {
    public boolean isSuccess() { return status == ExecutionStatus.SUCCESS; }
    // success/failure/ask/cancelled/budgetExhausted/timeout ... withMeta(...)
}
```

**工具**：`RuntimeTool { String name(); String description(); String parametersSchema(); ExecutionResult invoke(ToolCall, RuntimeContext); }`

**中间件**：`Middleware { default int order(); onLoopStart/beforeLlm/afterLlm/beforeTool/afterTool/onLoopEnd; }`

**策略**：`StrategyPlugin { int order(); boolean applies(ctx); shouldDecompose(ctx,llmOut); shouldSpawnSubAgents(ctx,llmOut); Verifier verifier(ctx,defaultVerifier); }`

**验证**：`Verifier { String name(); boolean objective(); VerificationOutcome verify(VerificationRequest); }`，
`VerificationOutcome(done, confidence, objective, evidence, summary, continueGoal)`

**记忆**：`MemoryPort { String recall(...); void recordLongTerm(...); void compact(...); }`（字段常量 goal/constraints/attempts/openQuestions/toolUsage）

**预算**：`BudgetManager { BudgetScope global()/task()/step()/subAgent(); void record(scope,tokens); Optional<String> globalExhaustedReason(); }`

**调度**：`SubAgentPool { <T> T submit(int depth, long timeoutMs, Callable<T> task); }`（虚拟线程 + 信号量背压 + 深度限制）

### 2.3 装配关系

`AgentRuntime = 中间件链 + 工具注册表 + 策略列表 + 验证器 + 记忆端口 + 子代理池`。
宿主通过注册 Bean 扩展：加一个 `Middleware` / `RuntimeTool` / `StrategyPlugin` / `Verifier` / `MemoryPort` 即可，主循环零改动。

## 3. 主循环重构代码

新主循环 `ThinAgentLoop`（`runtime/loop/ThinAgentLoop.java`）主体结构：

```java
for (int iter = 1; iter <= maxIter; iter++) {
    // ── 第 1 步：调 LLM（预算/日志/压缩等由中间件处理） ──
    if (!runtime.beforeLlm(loopCtx)) { /* 中间件阻断 → 预算耗尽返回 */ }
    EngineRunResult llm = engine.run(withSuppress(ctx, Phase.ACT, goal), Phase.ACT, goal).block();
    ExecutionResult llmResult = toExecutionResult(llm, rc, iter);
    loopCtx.result(llmResult); runtime.afterLlm(loopCtx);

    // ── 第 2 步：执行工具 / 子代理（策略决定，运行时执行） ──
    executeOrchestrationStep(rc, loopCtx, llmResult);

    // ── 第 3 步：回填观察 ──
    observations.append(...); stateManager.session(ref).appendMessage(UserMessage.from("【观察】" + brief(output)));

    // 达成度判定：运行时按「客观优先」选择验证器
    VerificationOutcome outcome = runtime.verifier().verify(VerificationRequest.of(goal, output));
    if (outcome.done()) {
        runtime.memory().recordLongTerm(...);              // 成功才沉淀
        return success(..., outcome.summary());
    }
    runtime.memory().compact(sessionId, structured);       // 失败只压缩
    goal = outcome.continueGoal() != null ? outcome.continueGoal() : goal;
}
```

对比原 `Orchestrator.run()`：**移除**安全阀内联判断（→ `BudgetMiddleware`）、ASK 分支（→ 统一 `ExecutionStatus.ASK`）、子代理规格构建/调度/回灌（→ 工具 + `SubAgentPool`）、重试/退避/回滚（→ 中间件/工具）、`isAskingReply`/`stuckLoop`（→ 收敛为最小循环守卫或策略）、验证与记忆内联调用（→ `Verifier` / `MemoryPort`）。

**启用方式**：`core.orchestrator-mode=thin`（默认仍为 `reactor`，旧实现保留，strangler 迁移）。

## 4. 迁移步骤（分阶段，低风险）

| 阶段 | 改什么 | 怎么改 | 风险点 | 回滚 |
|------|--------|--------|--------|------|
| **P1 统一契约与可观测性** | 引入 `ExecutionResult` / `ExecutionMetrics` / `TraceContext`；`EngineRunResult` 增加 traceId/spanId | 新增适配层把 `EngineRunResult` → `ExecutionResult`；不改现有调用 | 适配遗漏导致字段丢失 | 纯新增，零回滚 |
| **P2 抽离验证与记忆** | 新建 `Verifier` / `CompositeVerifier` / `ExternalCommandVerifier`、`MemoryPort` | 把 `verificationChain`/`loopMemoryManager` 包装为接口实现，主循环改调接口 | 客观验证命令需权限/边界（复用执行臂） | 保留旧链路开关 |
| **P3 工具化拆解与调度** | `RuntimeTool` + `ToolRegistry`；`Decompose/SubAgent/Verify/Memory` 工具；`SubAgentPool` | 拆解/子代理从主循环移出为工具；子代理改虚拟线程池 | 工具与主循环循环依赖（用端口/上下文解耦） | 工具与内联并存 |
| **P4 主循环减薄** | 落地 `ThinAgentLoop`，以 `core.orchestrator-mode=thin` 灰度 | 同接口并存，按会话/比例放量 | 行为差异（ASK/取消语义、goal 改写） | 切回 `reactor` |
| **P5 策略调优** | 插件化策略（拆分/子代理/验证器/预算档位） | 按任务特征装配不同 `List<StrategyPlugin>` | 策略冲突（order 仲裁） | 单策略兜底 |

**推荐灰度为：** 先 P1+P2（纯增强，不动主循环）→ P3（能力外置，双跑对拍）→ P4（切换主循环，保留回滚开关）→ P5。

## 5. Java 21 虚拟线程使用要点

1. **子代理/工具并发用虚拟线程**：`Executors.newVirtualThreadPerTaskExecutor()`（已用于 `SubAgentPool`）。适合「大量阻塞在 IO/模型调用」的子任务。
2. **必须背压**：虚拟线程数量不等于无限并发。用 `Semaphore` 限制在途子代理数（默认 4），否则会打爆模型配额/磁盘/下游服务。
3. **限制嵌套深度**：`submit(depth, ...)` 校验 `depth <= maxDepth`，防止子代理无限递归派生。
4. **不要用 ThreadLocal 传上下文**：虚拟线程数量巨大且生命周期可能很短，ThreadLocal 易泄漏且语义混乱。**改用 `ScopedValue`（Java 21 预览）或显式传参**（本项目用 `RuntimeContext` 显式传递 trace/预算，规避该问题）。
5. **线程安全**：子代理共享的 `BudgetManager`/`ToolRegistry`/`MemoryPort` 必须线程安全（`ConcurrentHashMap`/`AtomicLong`/`Semaphore`）；共享可变状态需 `snapshot` 隔离。
6. **同步原语**：`synchronized` 在虚拟线程上会 pin 载体线程，尽量用 `ReentrantLock`；避免在虚拟线程内做长时间 CPU 密集计算（应下沉到平台线程池/ForkJoin）。
7. **结构化并发**：需要「一组子任务全成功或全取消」语义时用 `StructuredTaskScope`（预览），保证无泄漏。
8. **超时**：`Future.get(timeout)` 或 `StructuredTaskScope` 的 deadline；超时后 `destroy/cancel` 并计入预算。

## 8. 实现完成情况（v2）

方案已**完整实现**，不再只是接口骨架。实现相对本文档设计有两处**刻意的调整**，均为工程上的改进：

### 8.1 调整一：中间件增加环绕钩子 `aroundTool`

原设计只有 before/after 通知型钩子（`beforeTool`/`afterTool`），但**重试类中间件无法通过通知型钩子实现**——它必须「再执行一次」真实调用。因此补充环绕式钩子：

```java
default ExecutionResult aroundTool(MiddlewareContext ctx, Supplier<ExecutionResult> next) {
    return next.get();   // 默认直通；实现方可多次调用 next.get()（重试）、跳过（缓存）、替换（降级）
}
```

`MiddlewareChain.aroundTool` 以**逆序折叠**组合，使 `order()` 最小者位于最外层。最终嵌套形态：

```
权限(-400) → 预算(-100) → 重试(500) → 压缩(600) → 召回(700) → 快照(900) → 日志(1000) → 工具实现
```

即：权限与预算**最先**决定放行、**最后**收到结果（且被拒不会重试放大）；日志在**最内层**，因此每次重试尝试都可观测。

### 8.2 调整二：验证能力改为**复用**既有实现，而非新建

初版在本包内另写了 `LlmJudgeVerifier`/`HeuristicLlmJudge` 等，随后发现 agent-core **已有**更成熟的验证子系统 `com.lucky.agent.core.util.verify`（`VerificationChain` + `FileVerifier`/`CommandVerifier` 经 `FileService` 受权限与执行臂边界约束 + 输出结构化 JSON 的 `LlmJudgeVerifier`）。为避免两套验证逻辑漂移，**删除了重复实现**，改为新增 `ChainVerifierAdapter`：

- `VerificationRequest` 增加 `RuntimeContext` 载体（验证器可访问会话上下文/事件发布器/预算）；
- 适配器据 `checkCommands` 与 `evidence.files` **合成 `Plan`**，喂给既有验证器，使 File/Command 客观校验真正生效；
- 无客观校验项时合成计划为 null，验证链自动降级为 LLM 整体判定——与「客观优先、主观兜底」一致。

最终验证链：`CompositeVerifier[ ChainVerifierAdapter(既有链) → FileArtifactVerifier → ExternalCommandVerifier ]`。

## 9. v3：剩余工作收口

### 9.1 模型调用侧韧性：`ModelGateway` 装饰链

`RetryMiddleware` 只能包裹**工具**调用，模型 API 调用（限流 429 / 网关 5xx / 连接重置 / 超时）此前完全没有退避与熔断。新增 `runtime/gateway/**`：

```java
CircuitBreakerModelGateway( RetryModelGateway( EngineModelGateway(engine) ) )
```

| 组件 | 职责 | 关键设计 |
|---|---|---|
| `ModelGateway` | 把「调模型」抽象为可装饰的单一方法 | `@FunctionalInterface`，失败以 `EngineRunResult.error` 表达（错误即数据） |
| `EngineModelGateway` | 最内层：`engine.run(...).block()` | 异常不外抛 → 转为 error 结果，外层只需判定结果 |
| `RetryModelGateway` | 指数退避 + ±25% 抖动 | **只重试瞬时故障**（429/5xx/timeout/connection）；401/403/参数错误等确定性失败**绝不重试**；`ask`/`cancel` 属业务语义不重试；退避倍数封顶 8× |
| `CircuitBreakerModelGateway` | 三态熔断 CLOSED/OPEN/HALF_OPEN | **只在状态迁移时持锁**，真实调用在锁外（否则熔断器会把所有会话串行化）；HALF_OPEN 只放行一个探测请求 |

熔断器处于**最外层**，因此 OPEN 状态下连带重试一起被短路——不会出现「已经熔断了还在退避重试」的配额浪费。

接入范围：`ThinAgentLoop` 与 `LangGraphOrchestrator` 直接用 `ModelGateway`；`ActScheduler` 也改为经网关调用，使**遗留 reactor 主环**同样白拿韧性能力。

### 9.2 双主循环收敛

`LangGraphOrchestrator` 原先自建一套「验证 + 早停 + 记忆 + 预算」，与 thin 主循环是两份实现，任何一处修改都会漂移。现改为复用同一套运行时：

| 原实现 | 现实现 |
|---|---|
| `engine.run(...)` 直接调用 | `ModelGateway`（重试退避 + 熔断） |
| `verificationChain.verify(...)` | `LoopController` → 运行时验证链（客观优先） |
| `earlyStopPolicy.shouldStop(...)` | `LoopController`（同一份早停语义） |
| `loopMemoryManager.manage(...)` | `LoopController` → `MemoryPort`（成功才沉淀/失败只压缩） |
| `RunBudget` 自建预算 | `RuntimeSessionFactory` 的全局四级预算 |

新增 `RuntimeSession` / `RuntimeSessionFactory` **统一引导过程**（预算 + `RuntimeContext` + `MiddlewareContext` + `onLoopStart/onLoopEnd` 生命周期）。此前两个主循环各自 `new` 一遍这三件套、各自记得调生命周期钩子，**任何一处漏改就是一次行为漂移**——这正是双主循环漂移的根源，现已收敛为一处。

`LoopController.decide(...)` 增加**计划感知重载**：langgraph 传入真实 `Plan` 时，客观验证按其 `verify` 声明逐步骤执行，从而在复用同一实现的同时**保持其原有验证语义**。

顺带修复：`LangGraphOrchestrator` 中记忆节点名被 IDE 重构污染为字符串字面量 `"com/lucky/agent/memory"`（IDE 把包名重写到了字符串里），已恢复为 `"memory"`。

### 9.3 验收压测 harness（零成本可复现）

新增 `RuntimeAcceptanceTest`（5 项）与 `ModelGatewayTest`（9 项）。模型由**脚本化 `Engine`** 提供（固定 token、固定轮次），因此可重复、零 API 成本。

| 验收项 | 断言内容 | 结果 |
|---|---|---|
| 四级预算独立熔断 | `SUBAGENT`/`STEP`/`TASK`/`GLOBAL` 四级分别耗尽；每级 token/时间/重试三类限制均可独立触发 | ✅ 通过 |
| 预算把循环挡在下一次模型调用之前 | 全局预算 100 token、每轮 60 token → 第 3 轮模型调用**从未发生**，返回 `budget_exhausted`，用量 120 | ✅ 通过 |
| 客观验证覆盖率 | 10 个语料（8 个声明真实落盘产物、2 个无证据）：整体覆盖率 **80% ≥ 70%**；可客观校验任务中客观路径生效 **100%**；有客观证据时置信度 = **1.0**；无证据时降级主观且置信度 < 1.0 | ✅ 通过 |
| token 消耗 | 同场景基线（主观自评，空转至迭代上限）5000 token vs 客观验证 2000 token → **↓ 60% ≥ 20%**；同时验证「失败轮只压缩 / 成功轮才沉淀」 | ✅ 通过 |
| trace 贯通与回放 | 快照 traceId 贯通率 **100%**，覆盖 before/after-llm 两个阶段，含 spanId 与预算用量 | ✅ 通过 |
| 模型侧韧性 | 瞬时故障重试恢复、401/ASK 不重试、退避 100→800ms 封顶、阈值 2 次转 OPEN 并短路委托、冷却后 HALF_OPEN 探测成功转 CLOSED、异常转 error 结果 | ✅ 通过 |

**测量口径（不夸大）**：

- 「token ↓ 60%」测量的是**早期终止**带来的省量（客观证据在第 2 轮确认达成即收尾，而基线只能空转到迭代上限）。**上下文压缩**带来的 prompt 缩减**未**计入——那需要真实模型与真实 prompt 统计，脚本化模型无法反映。
- 「客观验证覆盖率 80%」的分母是语料总数（含 2 个天然无法客观校验的任务）；对**可客观校验**的任务，覆盖率是 100%。两个数字同时给出，避免用分母选择制造好看的数字。
- 全部数字可用 `mvn -pl agent-core -Dtest='RuntimeAcceptanceTest,ModelGatewayTest' test` 在本机复现。

> ⚠️ **构建陷阱（本次踩到并被纠正）**：改签名为「构造器参数」或「record 组件」后，maven-compiler-plugin 的**增量编译不可靠**——未变更的类不会被重新编译，于是依赖它的旧 `.class` 仍引用旧签名，表现为测试运行时 `NoSuchMethodError`（本次 `ActScheduler.<init>(Engine)` 与 `VerificationRequest.<init>(String,String,List,Map,RuntimeContext)` 各命中一次），而 `mvn test` 表面仍是「编译通过」。
> 因此：**改公共签名后必须 `mvn clean test`**，否则本地绿灯不可信。

### 9.5 与此前「面试复盘缺口清单」的交集

本次重构对既有缺口清单的部分条目有直接影响，逐条标注以免误以为「已全部解决」：

| 既有缺口 | 现状 |
|---|---|
| 长任务模型递归列举失控（死循环） | **thin 侧已堵**：拆解上限 8 步、子代理深度 ≤2、单轮派发 ≤4、`SubAgentPool` 信号量背压。**reactor 侧仍缺**「每轮 `file.list` 预算上限」 |
| 模型 API 调用缺少外部重试/退避/熔断 | **已解决**：`ModelGateway` 装饰链，且三处调用点（thin / langgraph / `ActScheduler`）均已接入 |
| 双主循环漂移 | **已收敛**（§9.2），但 `reactor` 仍在用 `EarlyStopPolicy` 等旧件——**三套件未完全统一**，灰度完成后应删除旧件 |
| 早停在无客观信号任务上不触发（`evidenceConfidence` 恒返 0.5） | **运行时侧已改**：`LoopController` 的 ASK 条件改为**只看置信度**，不再要求 `!objective`，故极弱主观判定（< 阈值）也会转 ASK；**但 reactor 的 `Orchestrator.evidenceConfidence` 仍是 0.5 中性** → 两处口径**尚未统一到 reactor**，属遗留项 |
| 客观验证异常 ≡ 任务失败（误杀） | **仍存在**：`ChainVerifierAdapter` 桥接的是既有 `VerificationChain`，继承其「异常即 failed」语义。要根治需在**既有链**内区分「真未完成」与「验证不可达」，不属本方案范围 |
| 客观验证为条件生效（仅 `verify` 声明的步骤） | **仍成立**：`ChainVerifierAdapter` 合成计划时同样只对有 `checkCommands`/`evidence.files` 的项做客观校验。§9.3 的「80% 覆盖率」正是在此口径下测得，**不要**读成「所有任务都能客观验证」 |

**结论**：本次解决的是**架构与韧性**层面（薄主循环、统一契约、工具化、中间件、策略、四级预算、可观测、模型侧韧性、双主循环收敛）；**验证语义的精度**（误杀、条件生效）与 **reactor 旧件下线**仍是独立的后续工作。
