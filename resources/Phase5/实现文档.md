# Phase 5 实现文档：微服务演进（按需，非当前实现）

> 关联需求：§2.1 `@Remote` 标记、§2.2 演进预留、§11 微服务演进预案。
> 触发条件（§11）：单实例 CPU/内存/模型在途数持续打满，或需独立扩缩容某模块（如记忆检索）。

## 1. 阶段目标
当单机并发真正超出多模块单体承载时，按 §2.1 预留的 `@Remote` 边界将热点模块拆为独立服务。演进**只改部署拓扑与 `agent-common` 中并发/缓存抽象的实现**，不动业务模块代码。用户数据始终在本机工作空间，MySQL/MinIO 仍不引入。

## 2. 拆分边界（§2.1 / §11）
- 以 module 为粒度；被 `@Remote` 标记的接口即 RPC 边界。
- 典型拆分：`agent-core`（编排）、`agent-memory`（检索，最易成瓶颈）、`agent-model`（模型路由/限流）优先独立。

## 3. 引入组件（§11）
| 组件 | 角色 |
|---|---|
| SpringCloud + Dubbo | 服务治理 + RPC（替代模块内 Spring 注入） |
| Redis | 跨节点缓存/会话（替代本机 Caffeine，仍不存用户内容） |
| Sentinel | 服务间限流熔断（替代 §2.2 本地令牌桶） |
| RocketMQ | 仅当出现跨服务异步事件（如回退事件链）时引入 |

> MySQL / MinIO **仍不引入**：用户数据始终在本机工作空间（§3.0）。

## 4. 演进步骤
1. **接口标记**：业务模块接口加 `@Remote(serviceName)`，明确 RPC 边界（Phase1 已预留）。
2. **抽象切换**：`agent-common` 的 `ConcurrencyGuard`/`RateLimiter`/`CacheGuard` 提供 Redis/Sentinel 实现，业务代码零改。
3. **服务拆分**：按 `@Remote` 边界启动独立进程，Dubbo 注册；内核改为远程调用。
4. **数据一致性**：本机优先不变——用户工作空间/记忆/配置仍在用户本机；服务端仅承载编排/检索/路由等无用户内容的状态。

## 5. 验收点
- [ ] `@Remote` 接口可无缝从本地注入切到 Dubbo RPC。
- [ ] 记忆检索模块独立部署后，跨节点缓存走 Redis 且不存用户内容。
- [ ] Sentinel 限流熔断生效，替代本地令牌桶。
- [ ] 用户本机工作空间/记忆/配置路径与 Phase1–4 完全一致，未迁云端。
- [ ] 业务模块源码无改动（仅 `agent-common` 抽象实现替换）。

## 6. 技术需求方案与思路架构分析

> 本章对 Phase 5 微服务演进的触发、边界与演进策略展开架构分析（本阶段非当前实现，纯预案）。

### 6.1 演进触发条件（§11）
**需求**：何时该拆、拆什么。
**方案与思路**：
- **触发**：单实例 CPU/内存/模型在途数持续打满，或需独立扩缩容某模块（如记忆检索）。
- **典型拆分优先级**：`agent-core`（编排）/`agent-memory`（检索，最易成瓶颈）/`agent-model`（路由限流）优先独立。
- **核心约束**：用户数据始终在本机工作空间——**服务端只承载编排/检索/路由等无用户内容的状态**，不碰用户文件/记忆/配置。

### 6.2 拆分边界（§2.1 `@Remote`）
**需求**：平滑拆分，不动业务代码。
**方案与思路**：
- 以 module 为粒度；Phase1 已在对接口打 `@Remote(serviceName)` 注解，该注解即 RPC 边界。演进时 RPC 框架识别注解，业务模块源码零改。
- 这是 Phase1"微服务预留"设计的兑现——证明初期单体并非技术债，而是演进起点。

### 6.3 抽象切换（§2.2 演进预留）
**需求**：并发/缓存语义在分布式下保持一致。
**方案与思路**：
- `agent-common` 的 `ConcurrencyGuard`/`RateLimiter`/`CacheGuard` 提供 Redis/Sentinel 实现，业务代码零改——呼应 Phase1/Phase2 把并发手段封装为统一抽象的设计。
- `AgentEvent` 事件流、`AgentChannel`、会话状态模型（D19/D20）在演进中保持不变，只改部署拓扑与传输实现。
- 引入组件：SpringCloud+Dubbo（RPC）、Redis（跨节点缓存/会话，仍不存用户内容）、Sentinel（限流熔断，替代本地令牌桶）、RocketMQ（仅跨服务异步事件如回退事件链时）。
- **MySQL/MinIO 仍不引入**：用户数据始终在本机（§3.0），是演进不可破的红线。

### 6.4 数据一致性（本机优先不变）
**需求**：拆分后用户数据不漂云端。
**方案与思路**：
- 本机优先不变——用户工作空间/记忆/配置仍在用户本机；服务端仅承载无用户内容的状态。
- 一致性的关键不在"分布式事务"，而在"用户内容根本不在服务端"，天然规避跨节点用户数据一致问题。

### 6.5 回退与取舍
- `@Remote` 标记不强制启用，默认仍为模块内调用；若拆分运维成本过高可保留单体。
- **架构判定**：微服务是"能力选项"而非"必经阶段"；当前多模块单体已满足零托管 + 单机并发，演进只在真实瓶颈出现时触发——避免提前复杂化。
