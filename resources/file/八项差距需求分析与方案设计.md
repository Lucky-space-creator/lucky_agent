# Lucky Agent：八项差距需求分析与方案设计（已确认）

> 本文件基于 Claude Code 五层架构分析整理，目标是：Phase 1 先把 MVP 跑通，但底层架构、接口契约和执行边界现在定死；后续再做安全、成本等增量优化。能复用的第三方框架直接复用，不造轮子。

## 确认记录

2026-08-19 已全部确认，采用推荐方案：

| 编号 | 决策项 | 确认方案 |
|---|---|---|
| 〇 | 底层技术栈 | A：JDK 17+ / Spring Boot 3.x / Maven / LangChain4j + LangGraph4j（核心）+ Spring AI（辅助） |
| 1 | Hook 体系 | A：内部 Hook 契约先行，外部 Hook 后续 |
| 2 | 权限模型 | A：deny > ask > allow 规则链 |
| 3 | 子代理隔离 | A：LangChain4j/LangGraph4j 子代理 + 摘要返回 + 独立预算 |

| 5 | 提示词缓存 | A：静态/动态分界先行 |
| 6 | 工具调度 | A：ToolAnnotations + 只读并行/写串行 |
| 7 | 控制流 | A：ConversationStateManager + Flux<AgentEvent> |
| 8 | 通道抽象 | A：AgentChannel 契约先行 |

## 决策原则

1. **MVP 优先**：Phase 1 只交付可运行的基础闭环，不做过度实现。
2. **架构先定死**：模块边界、接口契约、事件协议、权限链、会话状态模型必须在 Phase 1 锁定，后续只能换实现，不能换结构。
3. **复用第三方**：优先复用 LangChain4j + LangGraph4j、Spring Boot/WebFlux、JGit、jtokkit 等成熟组件。
4. **本机优先**：用户数据始终在本机工作空间，不因复用框架而改变隐私边界。

## 〇、底层技术栈锁定（必须先定）

**现状问题**：当前需求文档写的是 Java + Spring Boot + LangChain4j/LangGraph4j，但没有锁定 LangChain4j/LangGraph4j 版本，也没有说明 LangChain4j/LangGraph4j 提供哪些能力边界。若不确定底层，后续所有设计都会漂移。

**方案选项**：

- A. Java 全栈：JDK 17+ + Spring Boot 3.x + Maven 多模块 + LangChain4j + LangGraph4j（核心）+ Spring AI（辅助）（LangChain4j 提供 Agent/工具/记忆/RAG，LangGraph4j 提供 StateGraph 工作流与多 Agent 编排，Spring AI 辅助提供模型/嵌入/向量库/可观测性）。
- B. Python 编排内核 + Java Web 壳：跨语言桥接，维护成本高，不建议。
- C. 完全自研编排：与“复用第三方”原则冲突，不建议。

**建议**：选 A。LangChain4j + LangGraph4j（核心）提供编排与工作流，Spring AI（辅助）提供模型/向量能力，我们只在其上做封装，不重复实现 REACT、子代理、权限与沙箱。

**锁定项**：

- JDK 17+、Spring Boot 3.x、Maven 多模块。
- LangChain4j + LangGraph4j 为核心 AI 技术栈，Spring AI 为辅助接入层。
- `agent-core` 只做编排封装，不自己实现第二套推理循环。

## 一、Hook 与生命周期强制切面

**需求**：在会话、用户输入、工具调用前/后、权限请求、子代理、压缩、停止等边界提供确定性切面，用于拦截、审计、格式化；多个 Hook 串行执行，任一拒绝即阻断（deny-wins）。

**方案选项**：

- A. Spring 事件/监听实现内部 Hook：定义统一 `AgentLifecycleEvent` + 有序监听器链，Phase 1 只做框架内部 Hook。
- B. 兼容外部 Hook（Shell/Webhook/MCP Tool）：对标 Claude Code 的 hook JSON 协议，后续开放给用户。
- C. 自研 Hook 引擎：重复造轮子，不建议。

**MVP**：只实现 A，预留事件名和输入输出契约。

**后续**：按契约接入 B，支持用户自定义 Shell/Webhook/MCP Hook。

**建议**：选 A，但事件清单现在定死：`SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / PreCompact / PostCompact / SubagentStart / SubagentStop / Stop`。

**架构锁定项**：

- 事件名、事件 JSON 结构、deny-wins 语义。
- `HookOutput = 控制流决策 + 上下文注入` 双层输出，避免模型被拦截后死循环。

---

## 二、权限 deny / ask / allow 规则引擎

**需求**：权限不只有“只读/修改/全部”，还需要可表达精确规则：`deny > ask > allow`，支持路径锚定、复合命令拆分、symlink 双路径检查和危险操作电路断路器。

**方案选项**：

- A. 轻量规则链：定义 `PermissionRule` 接口 + 有序规则链，MVP 支持路径规则（glob/regex）和命令规则（命令 token 化后匹配）；`PermissionDecision = ALLOW / DENY / ASK / DEFER`。
- B. 引入重型规则引擎（Drools/Easy Rules）：能力足够但复杂度高，MVP 阶段不建议。
- C. 维持三档权限：无法表达精确拒绝规则，不满足需求。

**MVP**：实现 A 的路径规则和基础命令规则，`deny` 永远胜出；`realpath` 规范化作为硬边界。

**后续**：补 symlink 双路径检查、复合命令拆分、OS 级沙箱、`bypass` 模式下的电路断路器。

**建议**：选 A。规则语义现在是架构级决定，规则来源可以是配置文件或 Hook 输出。

**架构锁定项**：

- 权限裁决顺序固定为 `deny > ask > allow`。
- 路径锚定语义：`//abs`、`~/home`、`/project-root`、`relative` 必须在文档和实现中一致表达。
- 所有文件/命令操作必须经过执行臂，执行臂是最终裁决者。

---

## 三、子代理上下文隔离与成本控制

**需求**：子代理在独立上下文窗口运行，只把摘要带回主 Agent；支持独立工具集、独立预算、可选 worktree 隔离；多 Agent 之间可异步通信。

**方案选项**：

- A. LangChain4j/LangGraph4j 子代理 + 自定义 `SubAgentSpec`：MVP 实现独立上下文、摘要返回、`maxTurns`/`maxTokens` 预算；worktree 隔离后续用 JGit 补。
- B. 自研子代理运行时：重复 LangChain4j/LangGraph4j 已有能力，不建议。
- C. 只用主 Agent 内联执行：不具备隔离能力，不满足需求。

**MVP**：A 的子集，串行/并行执行 + 摘要返回 + 独立预算；任务列表和进度展示同步落地。

**后续**：`model: inherit` 提示词缓存继承、JGit worktree 隔离、文件系统 Team + 异步 Mailbox 消息协议。

**建议**：选 A。`SubAgentSpec` 契约现在定死：`id / name / tools / disallowedTools / maxTurns / maxTokens / permissionMode / summaryOnly / isolation`。

**架构锁定项**：

- 子代理只能把摘要或结构化结果返回主 Agent，不直接回灌完整上下文。
- 子代理不提升权限，不绕过 ASK，不绕过执行臂硬边界。

---

## 四、多级上下文压缩流水线

**需求**：上下文不能只有“90% 阈值 + 摘要”一档，需要受控降级：单次工具结果裁剪 → 微压缩 → 紧急丢弃 → 主动摘要 → API 拒绝后激进兜底；压缩失败要有熔断。

**方案选项**：

- A. 定义 `CompactionPipeline` 接口 + 分级枚举，MVP 实现工具结果裁剪和基础摘要，后续逐级补齐。
- B. 沿用单档 90% 阈值：实现简单但不可靠，不建议作为最终架构。
- C. Phase 1 就做满五级：工作量大，与 MVP 原则冲突。

**MVP**：实现第一级“工具结果预算裁剪”和第四级“主动摘要”的最小版本，其余留接口。

**后续**：`Microcompact / Snip / Reactive Compact`、`preservedSegment` 保留最近 N 轮、`PreCompact/PostCompact` Hook 归档、连续失败熔断（如 3 次）。

**建议**：选 A。压缩流水线是接口级决定，实现可以按阶段演进。

**架构锁定项**：

- 压缩级别枚举固定为五级。
- 压缩前必须有 Hook 事件，压缩失败必须走熔断，不能无限重试。
- 压缩只能丢“过程”，不能丢“计划、安全约束、关键结果”。

---

## 五、提示词静态/动态分界与缓存

**需求**：系统提示词拆成静态可缓存部分和动态部分，通过边界标记和缓存断点最大化 prompt cache 命中；子代理可继承父会话缓存。

**方案选项**：

- A. 定义 `SystemPrompt` 组装层：静态 sections + 动态 boundary + 动态 sections；MVP 先定契约，是否真正使用 `cache_control` 取决于模型供应商支持。
- B. 直接拼接 prompt：无法做缓存和覆盖优先级，不建议。
- C. Phase 1 就做完整缓存策略：依赖具体模型供应商能力，过早。

**MVP**：实现组装层和边界标记，静态部分保持稳定；缓存断点在模型适配层预留。

**后续**：根据供应商 API 接入 `cache_control`，实现子代理 `inherit` 缓存继承，暴露 cache hit/miss 指标。

**建议**：选 A。这个决策成本很低，但直接影响后续 token 成本，越早定越好。

**架构锁定项**：

- 提示词五级覆盖优先级：Override > Coordinator > Agent > Custom > Default。
- 静态/动态边界标记必须稳定，任何动态内容不能混入静态前缀。

## 六、工具注解与并行调度

**需求**：工具需要声明 `readOnly / destructive / idempotent` 等注解，harness 据此自动并行只读工具、串行写工具；工具错误以数据返回，不抛异常崩循环。

**方案选项**：

- A. 扩展 `Tool` 契约 + `ToolAnnotations`：MVP 支持只读并行 + 写操作串行 + `ToolResult.isError` 返回协议。
- B. 维持现有简单 Tool 接口：缺少调度和错误契约，后续难扩展。
- C. 引入 LangChain4j/Spring AI 工具抽象：可考虑，但 LangChain4j 已有工具注册机制，优先复用。

**MVP**：A 的最小实现，只读工具并行、写工具串行、错误作为结果返回。

**后续**：工具结果预算、批量工具 Hook、按权限和语义过滤注入。

**建议**：选 A，工具注册复用 LangChain4j 的 Tool 机制。

**架构锁定项**：

- `Tool` 契约包含 `name / description / schema / annotations / execute`。
- 工具执行不允许向上抛异常，统一返回 `ToolResult { ok, data, error }`。

---

## 七、会话状态唯一事实源与控制流

**需求**：对话状态必须有一个唯一事实源；引擎对外暴露事件流，支持流式输出、取消、恢复，并在循环边界检查 `maxTurns`/`maxBudget`。

**方案选项**：

- A. `ConversationStateManager` + Project Reactor：LangChain4j/LangGraph4j 会话作为状态源，引擎以 `Flux<AgentEvent>` 输出，Web/CLI 消费同一事件流。
- B. 保留现有“循环 + SSE”两段式：状态分散，取消和恢复难做。
- C. 引入自研协程/生成器：Java 无原生 async generator，不必造。

**MVP**：实现 `ConversationStateManager` 和 `Flux<AgentEvent>`，SSE 消费该流。

**后续**：断点恢复、预算硬门槛、SDK 对外暴露同一事件流。

**建议**：选 A。Project Reactor 是 Spring 生态标准，直接复用。

**架构锁定项**：

- `AgentEvent` 类型固定：`thought / action / tool_result / skill_invoke / mcp_invoke / task_plan / task_progress / ask / error / token / stop`。
- 每次循环边界检查 `maxTurns` 和 `maxBudget`，不允许在循环内部判断预算。

---

## 八、多入口 Bridge 抽象

**需求**：Web 是当前入口，CLI 后续接入，SDK 远期可考虑；所有通道共用同一引擎和事件流，不能各自实现一套接入层。

**方案选项**：

- A. 定义 `AgentChannel` 契约：WebSSEAdapter、CliReactorAdapter 都消费 `Flux<AgentEvent>`；MVP 只实现 Web。
- B. 先做 Web，后补 CLI 时再抽象：改动风险高，与“架构定死”冲突。
- C. Web/CLI 各写一套：明确禁止。

**MVP**：只实现 `WebChannel`，但 `AgentChannel` 接口现在定义。

**后续**：CLI 用同一接口接入，终端渲染 `AgentEvent`；未来 SDK 复用同一事件流。

**建议**：选 A。接口成本很低，能避免后续重写。

**架构锁定项**：

- 通道只负责渲染和输入，不持有业务逻辑。
- 会话、任务、恢复协议由内核统一管理，通道只传 `AgentEvent` 和用户输入。

## 建议决策顺序

1. 先定第〇项：Java + Spring Boot + LangChain4j + LangGraph4j（核心）+ Spring AI（辅助）。
2. 再定第 7、8 项：会话事件流与通道契约，这是所有入口的底座。
3. 然后定第 1、2 项：Hook 事件名和权限链，决定安全边界。
4. 最后定第 3-6 项：子代理、压缩、缓存、工具注解，按阶段实现。
